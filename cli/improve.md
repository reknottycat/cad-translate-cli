# cli-anything-cad 优化方案

## 文档目的

这份文档不是简单的待办清单，而是站在当前项目实际状态上，对
`cli-anything-cad` 下一阶段演进方向的重新梳理。

当前这套 CLI 已经具备可用的基础能力：

- `DWG -> DXF -> extract -> apply` 主流程可跑通
- 统一配置系统已经落地
- LLM 支持主模型和备用模型
- 术语库、prompt 模式、reasoning 参数已经可配置
- 本地 release/build/smoke 流程已经具备

但从“能用”走向“顺手、稳定、可维护”，仍然有一段明显的优化空间。

## 重构背景（2026-03-25）

当前 CAD CLI 正在按 CLI-Anything 的 harness 标准重构（Click + REPL + JSON 输出 + 真实后端集成 + 测试/文档/发布闭环）。

CLI-Anything 作为开发参考的技能包保留，不是运行时依赖。

旧实现已归档到 `agent-harness/cad-translate_legacy/`，并且被刻意排除在运行时、打包和 pytest 扫描范围之外。

本优化方案仍然以“保留核心变量 + 先收敛骨架 + 再逐步回填 CAD 专项能力”为主线，避免在旧实现和新骨架之间来回切换造成冲突。

## 总体判断

我认为接下来最重要的，不是继续堆新功能，而是把这 5 个方向做扎实：

1. 首次使用体验
2. 配置系统闭环
3. DWG 后端诊断与选择
4. 翻译质量稳定性
5. 发布与运维可观测性

如果这 5 个方向做好，这个 CLI 才会从“工程样机”真正进入“可交付工具”的状态。

## 优先级建议

### P1：补齐首次运行引导

建议新增：

- `onboard`
- `onboard --scope global|project`
- `onboard --skip-llm`
- `onboard --skip-converter-check`
- `onboard --skip-glossary`

推荐默认行为：

- 默认目标语言：`ru`
- 默认翻译模式：`add`
- 默认 converter backend：`auto`
- 默认 system prompt：`cad_specialized`
- 默认优先启用术语库辅助翻译

为什么它最优先：

- 现在系统能力已经不少，但新用户第一次上手成本仍然偏高
- 用户需要自己理解 `config set`、`config llm init`、glossary、fallback 等概念
- `onboard` 可以把已有能力组织成一条首次配置路径，明显降低学习门槛

我认为这会是“用户感知提升最大”的一个改动。

### P2：把配置系统做完整

当前统一配置架构已经是对的，但还不算闭环。

建议继续补：

- `config unset <path>`
- `config set --scope global|project`
- `config open`
- `config edit`
- `config export`
- `config doctor`

为什么重要：

- 现在能读、能写、能校验，但还不够完整
- 项目级配置已经能读取，但还不能优雅地通过 CLI 写入
- 当配置出错时，用户仍然需要自己判断到底是哪一层生效

理想状态应该是：

- 看得见当前值
- 看得见来源
- 能快速修改
- 能快速回退
- 能快速诊断

### P3：增强 DWG 后端策略

当前 DWG 后端链路已经可用：

- `haochen_com`
- `autocad_com`
- `oda`

但“可用”不代表“透明”和“稳定”。

建议新增一层后端能力管理：

- 能力矩阵
  - 是否保图像
  - 是否依赖许可证
  - 是否适合复杂图纸
  - 是否仅 Windows 可用
  - 是否适合默认回退
- 轻量健康探测
  - 是否能启动
  - 是否能真正保存
  - 是否能完成小样本转换
- 健康缓存
  - 避免每次运行都重新探测全部后端

为什么重要：

- 你这个项目的痛点之一就是 DWG 转换后端差异非常大
- 目前的自动回退已经有用，但还不够“聪明”
- 用户需要的不是“试一遍看看”，而是“为什么选这个后端”

### P4：把翻译质量从“可配置”推进到“可控”

当前翻译层已经支持：

- glossary
- `default / cad_specialized / custom`
- 主备模型回退
- reasoning 开关

但术语稳定性仍然高度依赖模型本身。

建议下一步加强：

- 术语优先替换
  在送给模型前做轻量术语锁定，或在返回后做保守校正
- 未命中术语报告
  输出哪些词没有命中 glossary
- 翻译风格模板
  - `literal`
  - `engineering`
  - `compact-label`
- 专业词黑名单/白名单
  防止某些标签被“意译”

为什么重要：

- 当前系统在“连接和配置”层面已经很强
- 下一阶段真正限制使用体验的，是“术语一致性”
- CAD 场景用户通常比普通文本翻译更在意稳定和统一，而不是语言润色

### P5：把长任务做得更可感知

目前本地 CAD 处理步骤相对快，但在线翻译部分仍然容易让用户感觉“不确定”。

建议补：

- 批次进度显示
- 当前正在使用哪个 provider / model
- 是否发生了 fallback
- 中间结果保存
- 支持断点继续

为什么重要：

- 对用户来说，最糟糕的不是慢，而是“看不懂是在慢还是卡住了”
- 这类能力可以明显减少误判和重复操作

### P6：增强发布和支持能力

当前已经有：

- `release package-info`
- `release build`
- `release smoke`

建议继续补：

- `release verify`
- `doctor bundle`
  输出配置摘要、后端状态、版本信息
- `--version`
- 标准化 changelog 模板

为什么重要：

- 当前已经能本地构建，但定位问题仍要靠人工拼信息
- 真正进入交付阶段后，版本追踪和问题诊断会越来越重要

## 建议的实施顺序

我建议按下面顺序推进，而不是并行乱做：

1. `onboard`
2. `config unset / scope / open`
3. `doctor backends / doctor llm / doctor config`
4. glossary 强约束与翻译报告
5. 长任务进度与恢复
6. release/diagnostic 扩展

这个顺序的原因是：

- 先解决首次使用和配置闭环
- 再解决排障能力
- 最后再解决体验增强和交付能力

这样投入产出比最高。

## 我最推荐的下一步任务包

如果只让我选一组最值得立刻做的内容，我会推荐这一包：

- `onboard`
- `config unset`
- `config set --scope project`
- `doctor backends`

为什么推荐这一组：

- 它们直接围绕“首次使用 + 配置闭环 + DWG 诊断”展开
- 这些是当前系统里最影响体验、也最容易让用户困惑的部分
- 它们建立在现有架构之上，不需要推翻已有实现

## 最后建议

这个项目当前最正确的路线，不是追求“再支持更多 provider / 更多命令”，而是：

- 让现有命令更容易理解
- 让当前配置更容易管理
- 让 DWG 后端选择更透明
- 让翻译质量更可控
- 让发布和排障更可重复

换句话说，下一阶段的重点应该是“产品化收口”，而不是“功能横向扩张”。
